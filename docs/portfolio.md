# 포트폴리오 설명 문서

## 1. 프로젝트 한 줄 소개

주차차단기 유지보수 현장에서 발생하는 수리 리포트를 표준 데이터로 수집하고, 관리자 승인 후 외부 제출용 파일로 변환하며, 장비별 오류 재발률을 분석하는 Spring Boot 기반 백엔드 시스템입니다.

---

## 2. 프로젝트 문제 정의

기존 유지보수 보고 프로세스는 현장 기사가 클라이언트사 보고 시스템에 직접 접근할 수 없어, 카카오톡 등 메신저로 수리 내용을 전달하고 관리팀이 이를 다시 취합하는 방식으로 운영되었습니다.

이 구조에서는 다음과 같은 문제가 발생할 수 있습니다.

- 수리 내용 누락
- 사진, 장비 기번, 수리 시간 등 정보 불일치
- 리포트 승인 및 처리 이력 추적 어려움
- 장비별 반복 오류 분석 불가능
- 외부 보고 양식 변환 과정의 수작업 증가

본 프로젝트는 이러한 수동 보고 흐름을 백엔드 시스템으로 구조화하여, 현장 리포트 등록부터 승인, Export, 분석까지 하나의 흐름으로 관리할 수 있도록 설계했습니다.

---

## 3. 핵심 기능 요약

### 3.1 인증 및 권한 관리

Spring Security와 JWT를 사용해 인증 구조를 구현했습니다.

사용자 역할은 다음과 같이 구분했습니다.

| Role       | 역할      |
|------------|---------|
| TECHNICIAN | 현장 기사   |
| MANAGER    | 관리팀     |
| ADMIN      | 시스템 관리자 |

기사는 본인 리포트만 생성, 수정, 삭제, 제출, 재제출할 수 있고, 관리자는 전체 리포트를 검토, 승인, 반려, Export할 수 있도록 Role 기반 접근 제어를 적용했습니다.

---

### 3.2 리포트 상태 관리

유지보수 리포트는 업무 흐름에 따라 상태를 전이합니다.

```text
DRAFT → SUBMITTED → REVIEWING → APPROVED → EXPORTED
```

반려 시에는 다음 흐름을 따릅니다.

```text
SUBMITTED 또는 REVIEWING → REJECTED → RESUBMITTED → SUBMITTED
```

각 상태 변경 시 처리자, 처리 시각, 사유를 기록하여 감사 로그로 활용할 수 있도록 했습니다.

---

### 3.3 이미지 업로드

현장 수리 증빙을 위해 리포트별 다중 이미지 업로드 기능을 구현했습니다.

이미지는 수리 전, 수리 후, 기타 유형으로 구분하며, 파일 확장자, MIME type, 용량, 빈 파일 여부를 검증합니다.

삭제 시에는 DB 메타데이터뿐 아니라 실제 로컬 파일도 함께 삭제되도록 처리했습니다.

---

### 3.4 Export 기능

승인된 리포트를 외부 제출용 파일로 변환하는 Export 기능을 구현했습니다.

지원 포맷은 다음과 같습니다.

| Export Type | 확장자   |
|-------------|-------|
| JSON        | .json |
| CSV         | .csv  |
| EXCEL       | .xlsx |

Export 파일은 서버에서 UUID 기반 파일명으로 생성하고, `report_exports` 테이블에 실행자, 실행 시각, 파일 URL을 기록합니다.

---

### 3.5 분석 API

승인 또는 Export 완료된 리포트를 기준으로 장비별 오류 통계를 제공합니다.

구현한 분석 API는 다음과 같습니다.

| API                                   | 설명              |
|---------------------------------------|-----------------|
| GET /api/analytics/error-types        | 전체 오류 유형별 발생 횟수 |
| GET /api/analytics/devices/{deviceId} | 특정 장비의 오류 발생 통계 |
| GET /api/analytics/devices            | 전체 장비별 분석 요약    |

장비별 재발률은 특정 오류 유형 발생 횟수를 해당 장비의 전체 분석 대상 리포트 수로 나누어 계산합니다.

---

## 4. 기술적 의사결정

### 4.1 요청값 대신 인증 사용자 기반 처리

리포트 생성 시 `technicianId`를 요청 body로 받지 않고, JWT에서 인증된 사용자와 연결된 technician 정보를 사용했습니다.

이를 통해 사용자가 다른 기사 ID로 리포트를 생성하는 문제를 방지했습니다.

상태 변경, 승인, Export 처리자 역시 요청값이 아니라 현재 로그인한 사용자로 기록했습니다.

---

### 4.2 오류 유형을 Enum이 아닌 운영 테이블로 관리

초기 오류 유형은 seed 데이터로 등록하되, 실제 리포트에서는 `error_types` 테이블을 참조하도록 설계했습니다.

이를 통해 운영 중 새로운 오류 유형을 DB에 추가할 수 있고, 리포트와 오류 유형은 다대다 관계로 연결할 수 있습니다.

---

### 4.3 주요 처리 시점과 상태 변경 이력 분리

`repair_reports`에는 제출, 승인, Export의 주요 처리 시점을 저장하고, `report_status_histories`에는 전체 상태 변경 이력을 저장했습니다.

이렇게 분리함으로써 화면이나 Export에 필요한 주요 정보는 빠르게 조회하고, 상세 감사 이력은 별도 테이블에서 확인할 수 있도록 했습니다.

---

### 4.4 파일 메타데이터와 실제 파일 분리

이미지와 Export 파일은 실제 파일은 로컬 디렉터리에 저장하고, DB에는 접근 가능한 URL과 메타데이터만 저장했습니다.

이를 통해 추후 AWS S3, Cloudflare R2 같은 외부 스토리지로 확장하기 쉬운 구조를 만들었습니다.

---

### 4.5 Export 공통 DTO 설계

JSON, CSV, Excel은 출력 포맷은 다르지만 사용하는 데이터는 동일합니다.

따라서 내부 `RepairReport`를 외부 제출용 공통 DTO로 먼저 변환한 뒤, 각 포맷별 Generator가 해당 DTO를 파일로 생성하도록 분리했습니다.

---

### 4.6 분석 대상 데이터 기준 명확화

분석 API는 작성 중이거나 검증되지 않은 리포트를 제외하고, `APPROVED`, `EXPORTED` 상태의 리포트만 대상으로 집계했습니다.

이를 통해 관리자가 신뢰할 수 있는 확정 데이터만 통계에 반영되도록 했습니다.

---

## 5. 트러블슈팅 및 개선 경험

### 5.1 JWT 테스트 환경 분리

초기에는 `./gradlew build` 실행 시 테스트 환경에서 `.env`를 읽지 못해 JWT 설정값 누락으로 실패했습니다.

이를 해결하기 위해 `application-test.yml`을 추가하고, 테스트 클래스에서 `@ActiveProfiles("test")`를 사용해 테스트 전용 설정을 분리했습니다.

---

### 5.2 ObjectMapper Bean 누락 문제 해결

JSON Export 파일 생성기를 구현하는 과정에서 `ObjectMapper` Bean을 찾지 못해 애플리케이션 컨텍스트 로딩이 실패했습니다.

이를 해결하기 위해 Jackson 설정 클래스를 추가하고 `ObjectMapper`를 Bean으로 등록했습니다.

---

### 5.3 Export enum 변환 실패 예외 처리

지원하지 않는 `exportType` 값이 들어왔을 때 500 응답이 발생했습니다.

이를 `HttpMessageConversionException`으로 처리하여, 잘못된 요청은 400 Bad Request와 명확한 안내 메시지로 응답하도록 개선했습니다.

---

### 5.4 테스트 데이터 중복 문제 해결

Controller 테스트에서 고정 이메일과 전화번호를 사용하자, 반복 실행 시 DB 중복 제약으로 테스트가 실패했습니다.

이를 해결하기 위해 UUID 기반으로 고유 이메일과 전화번호를 생성하여 테스트가 반복 실행되어도 안정적으로 통과하도록 개선했습니다.

---

## 6. 줄글 설명

이 프로젝트는 현장 유지보수 보고 업무를 백엔드 시스템으로 구조화한 프로젝트로,
도메인 모델링, 인증/인가, 파일 업로드, 상태 관리, 예외 처리, 통계 쿼리, 테스트 코드 작성까지 백엔드 개발 전반의 흐름을 거쳤습니다.

실제 업무에서는 현장 기사가 클라이언트 시스템에 직접 접근하지 못해 메신저로 수리 내용을 전달하고, 관리팀이 이를 다시 정리해 보고하는 수동 흐름이 발생할 수 있습니다. 저는 이 과정에서 보고 누락, 사진이나 장비
기번 불일치, 처리 이력 추적 어려움, 반복 오류 분석 불가 같은 문제를 정의했습니다.

이를 해결하기 위해 Spring Boot 기반으로 리포트 생성, 이미지 업로드, 승인 워크플로우, 외부 제출용 Export, 장비별 오류 분석 API까지 하나의 흐름으로 구현했습니다.

특히 단순 CRUD에 그치지 않고, JWT 인증과 Role 기반 권한 제어를 적용해 기사와 관리자의 업무 범위를 분리했습니다. 또한 리포트 상태 전이를 통해 제출, 검토, 승인, 반려, 재제출, Export 흐름을
관리하고, 각 처리자와 처리 시각을 기록해 추적 가능성을 높였습니다.

Export 기능에서는 내부 리포트 데이터를 외부 제출용 DTO로 변환한 뒤 JSON, CSV, Excel 파일로 생성하도록 구조를 분리했습니다. 분석 API에서는 승인 또는 Export 완료된 리포트만 대상으로
장비별 오류 발생 횟수와 재발률을 계산해, 운영 의사결정에 활용할 수 있는 데이터를 제공하도록 했습니다.
